# EasyEAP security

EasyEAP controls who gets onto a network, so its failures must deny rather than permit, and its secrets must stay
where they belong. This document describes the threat model, how keys and secrets are held, and the controls in
the code. Report vulnerabilities privately to the maintainers. Don't open public issues for them.

## Threat model

| Asset | Threats | Main controls |
|---|---|---|
| Tenant Root CA key | Theft would let an attacker mint trusted client and server certificates | Generated in a temporary OpenBao mount during the ceremony, returned **once** as an encrypted PKCS#8 file (passphrase ≥ 12 characters, chosen by the administrator), then destroyed by unmounting. EasyEAP keeps no copy. Lab mode can keep it online, and is labelled insecure. |
| Tenant Issuing CA key | Same, within the CA's lifetime | Generated inside OpenBao (`type=internal`), never exported. The API holds a policy-limited, renewable token; the OpenBao root token is revoked after bootstrap. |
| Client private keys | Impersonation of a user or device | Generated on the device by default: WebCrypto in the enrollment portal, or the Windows helper with the TPM when one is present. The opt-in server-generated mode wraps the key in a password-protected PKCS#12 (AES-256-CBC, PBKDF2-SHA256, 600,000 iterations), encrypts it with the tenant's Transit key, and allows one download before purging. An undelivered package expires, and its certificate is revoked. |
| RADIUS shared secrets | NAS spoofing, offline cracking of captured RADIUS traffic | Generated by EasyEAP (32 random characters), shown once, stored only as Transit ciphertext, and delivered to the RADIUS agent over the authenticated channel (written 0600 on the RADIUS volume). Never displayed again; rotation creates a new one. |
| AD bind password | Directory read access | Write-only in the console ("leave blank to keep"), stored as Transit ciphertext, never returned by the API or logged. A read-only service account is recommended and documented. |
| Administrator accounts | Takeover of the console | No default account: the first administrator is created with a one-time setup token from the server. Argon2id hashing (time 3, memory 64 MiB, parallelism 2), a 12-character minimum with checks against the email and repetitive passwords, TOTP second factor, lockout after 8 failures for 15 minutes, sign-in rate limit of 10 per minute per IP and 20 per 10 minutes per email. |
| Tenant isolation | One customer reading or changing another's data | PostgreSQL row-level security on every tenant table, set per transaction by an `after_begin` listener; the application connects as a non-owner, `NOBYPASSRLS` role. Per-tenant PKI mounts and Transit keys. RADIUS clients route to their own tenant's virtual server, with its own trust anchors. |
| Authorization decisions | Granting access when data is missing or stale | Fail closed: unknown certificate serial → reject; snapshot older than the tenant's maximum age → reject everyone (`snapshot_stale`); account disabled, locked or deleted in AD → reject. Deny rules always win. The tenant default is Deny. |
| Audit trail | Tampering after the fact | Each row stores `sha256(previous hash ‖ canonical row)`; UPDATE and DELETE are revoked from the application role; the chain is verifiable from the console and with `easyeap verify-audit`. |

## Key custody summary

| Key or secret | Where it lives | Who can read it |
|---|---|---|
| Root CA private key | Offline only (the administrator's encrypted file) | Whoever holds the file and passphrase |
| Issuing CA private key | OpenBao PKI mount `pki-t-<tenant>` | Nobody; OpenBao signs with it |
| RADIUS server private key | Transit ciphertext in the database; plaintext only on the RADIUS volume (0600) | The RADIUS agent |
| Tenant secrets (shared secrets, bind password, escrowed PKCS#12) | Transit ciphertext (key `t-<tenant>`) in the database | The API, through its OpenBao token |
| Admin TOTP secrets | Transit ciphertext (platform key) | The API, at verification time |
| OpenBao seal key | The PKI's `easyeap-pki-seal` volume (seeded once from `deploy/secrets/openbao_unseal_key`) and, encrypted, inside each backup | The PKI container; root on the host |
| OpenBao recovery keys | The API's secrets volume (0600), on installations made with 1.0.0 or later | The API |
| OpenBao API token | The API's secrets volume (0600) | The API and worker |
| Database passwords, agent token, session HMAC key | `deploy/secrets/*`, mounted as Compose secrets | The containers that need each one |

### Backups

A console backup is **complete by design**: the database, the OpenBao storage with every issuing CA key, its seal
key, and the API's secrets. That makes the backup file, together with its passphrase, as sensitive as the CAs, and it
is a deliberate exception to "CA keys never leave OpenBao". The controls:

- Only a Super Administrator can create, download or restore one. Creating and restoring need their password and
  two-factor code again. Every step is audited (who, when, size and the file's SHA-256).
- Backups are always encrypted with age (scrypt for the passphrase, authenticated streaming encryption for the
  contents). There is no unencrypted option. Passphrases are at least 12 characters with at least 5 distinct ones,
  EasyEAP can generate one, and the passphrase is never stored or logged.
- The database dump is encrypted as it streams; the PKI archive is in plaintext only on a tmpfs volume shared by the
  API and PKI containers, for seconds. The server keeps the encrypted file for 24 hours so it can be downloaded,
  then deletes it.
- Restoring checks the whole file before changing anything, keeps the previous database, PKI and secrets until the
  new ones are verified, and rolls back on any failure. It signs everyone out. A first-run restore needs the
  installer's setup token, so a fresh server can't be claimed by restoring someone else's backup onto it.

### Logs and syslog

The system log (30 days in the database) and remote syslog carry operational messages, the audit trail and
authentication events: user names, MAC addresses, NAS addresses, certificate serials, VLANs and reasons. They never
carry secrets, keys or passwords: every line passes the same redacting filter before it's stored or sent. Use TLS
for remote syslog so this metadata isn't readable on the network; the console warns when TCP or UDP is chosen. A
TLS destination's certificate and host name are always verified (TLS 1.2 or later), against a pasted CA or the
system's trust store.

## Controls in the code

- **No custom cryptography.** X.509 issuance and CRL/OCSP come from OpenBao; parsing and packaging from pyca/cryptography; in-browser key generation from WebCrypto; CSR/PKCS#12 assembly from PKI.js; password hashing from argon2-cffi; TOTP from pyotp.
- **EasyEAP is the registration authority.** The CSR's subject and SANs are ignored. Names come from directory data and the template, so a user can't request a certificate for someone else.
- **One certificate per device.** Enrollment links are bound to tenant, identity and device name, single use, and expire (72 hours by default). The 256-bit token is stored only as a SHA-256 hash. The hash is kept after use so the portal can say "already used", but every action on a used, cancelled or expired link is refused (410). Requests are rate-limited per address and per link.
- **PKCS#12 passwords.** The portal generates a 92-bit password (or the user sets one of at least 8 characters for a file that never leaves the device). Server-generated packages use a 119-bit password. With passwords of that strength, the 2,048-iteration PKCS#12 MAC (the OpenSSL default, kept for device compatibility) is not the weak point.
- **Sessions.** Random 256-bit token in a `Secure`, `HttpOnly`, `SameSite=Strict` cookie, stored hashed server-side, 12-hour lifetime. Every unsafe request needs the per-session CSRF token (an HMAC of the session) in `X-CSRF-Token`. Changing a password ends the account's other sessions.
- **RBAC.** Platform roles apply to all tenants; tenant roles are granted per tenant. Issuing certificates and managing CAs are separate permissions. Turning on server-generated keys requires a Tenant Administrator. The console hides actions a role can't take; the API enforces them regardless.

| Permission | Wi-Fi Admin | PKI Admin | Tenant Admin | Auditor |
|---|:-:|:-:|:-:|:-:|
| Read everything in the tenant | ✓ | ✓ | ✓ | ✓ |
| Issue / revoke certificates, manage enrollment links | ✓ | ✓ | ✓ | |
| Edit access policy and VLANs | ✓ | | ✓ | |
| Configure RADIUS, add controllers (secret shown once at creation) | ✓ | | ✓ | |
| Rotate RADIUS shared secrets | | | ✓ | |
| Configure the directory | | | ✓ | |
| Run a directory sync | ✓ | | ✓ | |
| Manage CAs and templates | | ✓ | ✓ | |
| Allow server-generated keys | | | ✓ | |
| Tenant settings | | | ✓ | |

MSP Operators have Tenant Administrator rights in every tenant, can create tenants, and can read System health and the platform audit. Super Administrators can also manage administrators (including resetting a lost second factor, which ends that administrator's sessions) and delete tenants. MSP Auditors are read-only everywhere.

- **Staged policy changes.** Rule changes are previewed against the real directory and published atomically. A stale draft is refused (409), and the impact summary is audited.
- **Logging.** A redacting filter strips passwords, secrets, tokens, bearer headers and PEM private keys from every log line as defence in depth; the code never logs them intentionally. RADIUS events never include shared secrets or key material.
- **Web hardening.** HSTS, a strict Content Security Policy (`script-src 'self'`, no inline scripts, `frame-ancestors 'none'`), `X-Content-Type-Options`, `Referrer-Policy: no-referrer`, Permissions-Policy and COOP on every response from the proxy. The API is never published directly; `/api/agent/` is not reachable through the proxy.
- **RADIUS hardening.** `require_message_authenticator` and `limit_proxy_state` on every client (Blast-RADIUS, CVE-2024-3596). TLS 1.2 minimum, configurable to 1.3. The TLS session cache is off by default, so resumption can't bypass the snapshot check. Controller source addresses must be unique across tenants that share ports.
- **Containers.** Every service runs as a non-root user; internal networks have no route out; only the proxy (80/443) and RADIUS (UDP 1812/1813 and the dedicated range) publish ports. RADIUS has no route to the database or OpenBao.

## Revocation: what "revoked" means in practice

Revoking a certificate updates the CRL and OCSP at once and republishes the tenant's authorization snapshot. RADIUS applies it within about 15 seconds (the agent polls the API every 15 seconds). From then on, **new** authentications with that certificate are rejected. A device that is **already connected** stays connected until:

- EasyEAP sends a CoA Disconnect-Request, when the controller has CoA enabled and the administrator chose to disconnect; or
- the session reaches its `Session-Timeout` and the device must re-authenticate (8 hours by default, configurable per tenant). Fast-roaming caches (PMK caching, OKC, 802.11r) can let a connected device roam without a full EAP exchange until then.

The console states this wherever revocation happens, and never claims revocation is immediate.

## Operating securely

- Replace the self-signed console certificate (`deploy/secrets/tls.crt` and `tls.key`) with a trusted one.
- Bind the published ports to internal interfaces where possible (`EASYEAP_*_BIND` in `.env`). RADIUS/UDP must not cross untrusted networks: use a site-to-site VPN.
- Turn on two-factor authentication for every administrator (Account page).
- Store each tenant's root key file and passphrase offline, separately, as you would any CA key.
- Make a backup from the console at least weekly (the dashboard warns after 7 days), keep the file off the server
  and its passphrase somewhere else, and test a restore on a spare server from time to time. `deploy/backup.sh`
  can schedule them.
- Forward the audit trail to a remote syslog server or SIEM over TLS, so a copy of it exists outside EasyEAP.
- Never enable lab mode or the lab profile on a production host.
